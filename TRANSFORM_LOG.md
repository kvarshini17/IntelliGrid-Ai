# IntelliGrid AI — Transform Log (Phase 0)

This document records exactly how `data/processed/intelligrid_energy_dataset.csv`
and `data/processed/room_reference.csv` were derived from the uploaded source
file. It is the single authoritative reference for what is original data, what
is a verified derivation, what is a regenerated field, and what is a
documented project assumption. Nothing in the processed dataset should be
cited in any report/paper without first checking this file.

Generated by: `scripts/preprocess.py` (seed = 42), validated by `scripts/validate.py`.

### Fields removed and why

| Removed field | Reason |
|---|---|
| `source_day_of_week` | Statistically indistinguishable from random noise: 12.1% agreement with the actual timestamp-derived weekday, versus a 14.3% chance baseline for 7 equally-likely categories. Not usable for any analysis. |
| `Room` (old) | Was assigned by `row_index % 10`, which aliases exactly with the 24-hour clock (`gcd(10,24)=2`): each old "room" only ever appeared at either even or odd hours. | `square_footage` (old, per-row) | Varied randomly row-to-row even under the same old `Room` label (range ~1013-1999 within a single room). Replaced by a fixed per-room value from the room reference table. |
| `hvac_on` | Exact redundant 0/1 encoding of `hvac_usage` (100% consistent cross-tab, verified before removal) |
| `lighting_on` | Exact redundant 0/1 encoding of `lighting_usage` |

## 3. Room reference table & assignment algorithm

### 3.1 Room reference table (`room_reference.csv`)

| room_id | floor | square_footage_fixed | capacity |
|---|---|---|---|
| Room 101 | 1 | 1000 | 10 |
| Room 102 | 1 | 1100 | 11 |
| Room 103 | 1 | 1200 | 12 |
| Room 104 | 1 | 1300 | 13 |
| Room 105 | 1 | 1400 | 14 |
| Room 201 | 2 | 1600 | 16 |
| Room 202 | 2 | 1700 | 17 |
| Room 203 | 2 | 1800 | 18 |
| Room 204 | 2 | 1900 | 19 |
| Room 205 | 2 | 2000 | 20 |

- `floor`: parsed from the first digit of the room number (an encoding of
  the existing naming convention, not an assumption).
- `square_footage_fixed`: **deterministic, evenly-spaced values** from 1000
  to 2000 sq ft (the approximate range observed in the original file),
  chosen over a seeded random draw so the figure requires no further
  justification beyond "evenly spaced within the originally observed range."
- `capacity`: `round(square_footage_fixed / 100)`. **Documented assumption**:
  100 sq ft per occupant, a coarse commercial-space planning figure. This
  value is descriptive metadata only and is never used to alter `occupancy`.

### 3.2 Room assignment algorithm

Each of the 1000 records is assigned a `room_id` using a per-hour balanced,
seeded, reproducible procedure (full code in `scripts/preprocess.py`,
function `assign_rooms_balanced_per_hour`):

```
for each hour h in 0..23:
    rows_at_hour_h = rows where timestamp.hour == h, sorted chronologically
    n = count of such rows

    rotation = h % 10
    rotated_room_ids = ROOM_IDS[rotation:] + ROOM_IDS[:rotation]
    # rotating the room order per hour prevents the "remainder" room
    # (when n is not an exact multiple of 10) from always being the
    # same one or two rooms across every hour

    reps = ceil(n / 10)
    pool = (rotated_room_ids * reps)[:n]       # exact balance within this hour
    rng = numpy.random.RandomState(42 + h)      # reproducible, independent per hour
    rng.shuffle(pool)

    assign pool[i] -> rows_at_hour_h[i] in chronological order
```

This replaces the original file's `row_index % 10` scheme, which produced a
hard period-10 alias against the 24-hour clock (verified in the pre-transform
audit: each old room only ever appeared at either even or odd hours, with
zero exceptions across all 1000 rows).

**An earlier, non-rotated version of this algorithm was tried first and
rejected** before this final version was approved: without rotating the room
order per hour, the first 1-2 rooms in the fixed list (`Room 101`, `Room
102`) always absorbed the "remainder" slot whenever an hour's record count
wasn't an exact multiple of 10, producing a systematic overrepresentation
(120 and 112 total records respectively, versus ~100 for every other room).
The rotation fix (`rotation = h % 10`) was added specifically to eliminate
this, and is confirmed working in the validation results below.

## 4. Documented assumptions

| Assumption | Statement |
|---|---|
| Electricity Tariff ToU bands | Hours 0-5 and 23 -> 5.0 (off-peak); hours 6-17 -> 7.0 (standard); hours 18-22 -> 9.0 (peak). This structure was already present in the uploaded file (verified 100% consistent against `hour` with zero exceptions) and is retained unchanged. It is a project assumption about tariff structure, not a real utility's published rate schedule. |
| `holiday` field | Synthetic, independently-sampled binary flag. Not tied to any real public-holiday calendar or to weekends (verified: ~46-47% "Yes" regardless of day type). Must be described as such wherever used. |
| Room capacity | `round(square_footage_fixed / 100)` — 100 sq ft/occupant is a coarse planning heuristic, not a measured or sourced figure. |
| `renewable_energy` unit | **No authoritative source documentation was available** for this uploaded file (no accompanying README, metadata, or source link was provided). The unit is therefore an **explicit, unverified project assumption**, not measured or sourced data. For internal consistency with `energy_consumption`'s implied unit, it is treated as kWh in any calculation that requires a unit — but this must be stated as an assumption everywhere it is used, including in any future paper's dataset-construction section. If an authoritative source is identified later, this section must be updated and the assumption re-evaluated (no recalculation of existing values would be needed unless the true unit turns out to be non-linearly different, e.g. not already a rate-equivalent of kWh). |

## 5. Known limitations carried forward from the pre-transform data quality audit

- **No wastage-magnitude signal in this dataset.** `energy_consumption` under
  the classic "wastage" condition (`occupancy == 0 AND hvac_usage == "On"`,
  n=44 in the original file) has a mean of 77.26, statistically
  indistinguishable from the overall mean of 77.06. The dataset's generation
  process did not build in a consumption penalty for this condition.
  **`energy_consumption` was NOT modified to manufacture such a signal** —
  per explicit instruction, the absence of this signal is treated as a
  transparent property of the dataset, not a defect to be hidden. Wastage
  detection will therefore be evaluated by condition-match precision/recall
  under controlled synthetic fault injection (Phase 3+), not by consumption
  magnitude.
- **No ground-truth wastage or anomaly labels exist in the original dataset.**
  None are claimed. Any future evaluation numbers come from a documented
  synthetic fault-injection protocol, never from an assumed label in this
  file.
- **CSV re-read hazard for the `appliance` column.** `pandas.read_csv()`'s
  default `na_values` list includes the literal string `"None"`. Any code
  that reads `intelligrid_energy_dataset.csv` with default `pandas.read_csv()`
  arguments will silently convert the intentional `"None"` appliance label
  back into `NaN`. **Every loader for this file (including the Phase 1
  `data_manager` module) must use `pd.read_csv(path, keep_default_na=False,
  na_values=[""])`** or equivalent, or re-derive missingness explicitly.
  This was caught during validation (see Check 7 note below) and must not
  be reintroduced.
